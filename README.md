# ap5 — コード中心の最小UEサンプル

Windows上でスクリプトを実行すると、床・検証用モンスター1体・TPSプレイヤー・照明をC++で生成します。
モンスターは19個の楕円体の体積を合成したゴーレム状のモデルです。外部の3Dモデルは不要で、外皮・穴の内壁・切断面をコードから生成します。
Blueprint作成、手動のモデル配置、手動のマップ保存は不要です。

## 対象環境

- Windows 11 x64、Windows PowerShell 5.1またはPowerShell 7（WSLでは実行しません）
- Unreal Engine **5.6.x**：Epic Games Launcherのインストール済みバイナリ版
- Visual Studio 2022のC++ビルドツール（17.8以上、17.14推奨）
- MSVC v143 **14.38（VS 17.8）**、Windows SDK **10.0.22621.0**
- DirectX 11 / Shader Model 5対応GPUとドライバ
- 最初の依存ソフト取得にはインターネット接続とインストール権限

最新UEを自動採用せず、再現性のため5.6系を明示しています。他バージョンはスクリプトが拒否します。
UEとビルドツールは大容量です。必要容量は各インストーラーの表示を確認してください。
一般のPython、Docker、Visual StudioのIDE画面操作は必須ではありません。

## 1. リポジトリ取得（WindowsのPowerShell）

Gitがなければ `winget install --id Git.Git --exact --source winget` で導入し、PowerShellを開き直します。
GitHub認証を求められたら、リポジトリへアクセスできるアカウントで認証してください。

```powershell
git clone https://github.com/SuzukiReiya/ap5.git
cd ap5
```

初回は短いローカルパス（例：`C:\dev\ap5`）を推奨します。OneDriveやネットワークドライブは避けてください。

## 2. 環境構築（WindowsのPowerShell）

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Scripts\Setup.ps1
```

このコマンドは、そのプロセス内のみ実行ポリシーを指定します。PC全体の実行ポリシーは変更しません。
会社のポリシー等で禁止されている場合は管理者に確認してください。

`Setup.ps1` は次を行います。

1. VS 2022＋MSVC 14.38が見つからなければ、wingetでBuild ToolsとSDKのインストールを開始。
2. UE 5.6を探し、未導入ならEpic Games Launcherのインストールを試み、手動工程を案内して終了コード1で停止。
3. UE・MSVC・SDKが揃ったら、UEのパスを `.local/engine.json` に保存。
4. `SETUP_READY` と表示して終了コード0で完了。

UAC、ソフトウェアのライセンス、インストーラー画面での確認が必要になる場合があります。
ライセンス同意はスクリプトで代行しません。再起動を要求された場合は再起動後に再実行してください。

### `SETUP FAILED: Manual step...` と表示された場合

次の順で表示された場合は、**最初からやり直したり、導入済みソフトを削除したりする必要はありません**。

| 表示 | 意味 |
|---|---|
| Visual Studio Build Toolsの「インストールが完了しました」 | Build Toolsのインストーラーは正常終了 |
| `WARNING: UE 5.6.x was not found...` | UE本体が未導入、またはインストール先を検出できていない |
| Epic Games Launcherの「インストールが完了しました」 | Launcherの導入は完了。UE本体の導入とは別 |
| `SETUP FAILED: Manual step: open Epic Games Launcher...` | UE本体の手動導入待ち。準備未完了を示すため、スクリプトが終了コード1で停止 |

赤字の `FAILED` はこの場合、直前のBuild ToolsやLauncherのインストール失敗を意味しません。
MSVC・SDKを含む最終チェックはUEが見つかった後に行うため、まだセットアップ完了ではありません。
警告中の `D:\Epic Games\UE_5.6` は指定例であり、その場所にインストールする必要はありません。

再開手順：

1. **Windowsのスタートメニュー**からEpic Games Launcherを開く。
2. **Launcher画面**で、次節の手順に従ってUE **5.6系** をインストールし、完了を待つ。
3. **WindowsのPowerShell**で、リポジトリのフォルダ（例：`D:\work\ap5`）へ戻り、同じコマンドを再実行する。

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Scripts\Setup.ps1
   ```

4. `SETUP_READY` が表示されたら、ビルドして起動する。

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Scripts\BuildAndRun.ps1
   ```

UE 5.6を既に導入済みなら再インストールせず、次節の `-EngineRoot` で実際のインストール先を指定してください。
再実行では検出できたMSVC 14.38のインストールをスキップします。別のエラーが表示された場合は、その内容に対応してください。

### 初回のみ手動：UE本体の導入（Epic Games Launcher画面）

今回の導入方法では、**Epic Games Launcherの起動とEpic Gamesアカウントでのサインインが必要**です。
アカウントを持っていない場合は、Launcherの「アカウントを作成」から登録してください。既存アカウントがあれば新規登録は不要です。
「後でサインイン」ではUE本体をダウンロードできません。

LauncherはUE本体のダウンロード・更新管理に使用します。インストールとセットアップが完了した後の通常のビルド・ゲーム起動は、`BuildAndRun.ps1` がUEの実行ファイルを直接呼び出すため、毎回Launcherから起動する操作は不要です。

1. Epic Games Launcherを開き、Epic Gamesアカウントを作成するか、既存アカウントでサインイン。
2. **Unreal Engine → ライブラリ → エンジンバージョンの「＋」**。
3. バージョン一覧から **5.6系** を選び、規約等を確認してインストール。
4. **Windows用エンジン本体とEngine Contentを残す**。Android/iOS等の追加プラットフォームは不要。
5. インストール完了後、PowerShellで `Setup.ps1` をもう一度実行。

Epicログイン・規約同意・UE本体のダウンロード指定は完全自動化していません。
Launcherの配置が標準外で再インストール案内が出る場合も、既存のLauncherを使って構いません。

UEを標準と異なる場所に導入した場合：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Scripts\Setup.ps1 -EngineRoot "D:\Epic Games\UE_5.6"
```

`EngineRoot` は `Engine` フォルダの**親**です。次回から保存されたパスを利用します。
検索優先度は `-EngineRoot` → 環境変数 `AP5_UE_ROOT` → `.local/engine.json` → レジストリ → 標準パスです。

### VSが既にあり自動追加に失敗した場合（Visual Studio Installer画面）

既存のBuild Toolsではwingetが「導入済み」と判断し、追加コンポーネントを入れないことがあります。
**Visual Studio Installer → VS 2022 / Build Tools 2022 → 変更**から次を追加してください。

- C++によるデスクトップ開発（Build ToolsではC++ビルドツール）
- 個別のコンポーネント：MSVC v143 - VS 2022 C++ x64/x86 ビルドツール **v14.38-17.8**
- 個別のコンポーネント：Windows 11 SDK **10.0.22621.0**

既にMSVC 14.38があってSDKだけ不足している場合も、SDKを上記の画面から追加してください。
その後 `Setup.ps1` を再実行します。既存のVSやSDKを削除する処理はありません。

導入処理をせず確認だけ行う場合：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Scripts\Setup.ps1 -CheckOnly
```

## 3. ビルドして実行（WindowsのPowerShell）

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Scripts\BuildAndRun.ps1
```

処理順序：

1. UnrealBuildToolで `Ap5Editor / Win64 / Development` をコンパイル。
2. 初回はUE同梱Pythonをコマンドレットから実行し、空マップ `Content/Generated/Minimal.umap` を保存。
3. UEの `-game` モードで1280×720のゲームウィンドウを起動。
4. C++で床・モンスター・TPSプレイヤー・ライトを生成。

初回はシェーダーコンパイルなどで時間がかかります。完了するまで待ってください。
再ビルド前に前のゲームやUEエディタを終了してください（DLLが使用中だとリンクに失敗します）。

同じPCでself-hosted GitHub ActionsのUEビルドとローカルビルドが重なると、runnerの `NetworkService` と対話ユーザーでUBTの `Global\\UnrealBuildTool_Mutex_*` のACLが異なるため、`-WaitMutex` でも `UnauthorizedAccessException` になる場合があります。`BuildAndRun.ps1` はこの特定のMutex競合だけを最大5分、10秒間隔で自動リトライします。通常のコンパイルエラーはリトライしません。

**この起動は開発用のStandalone Gameです。配布用exeではなく、UE本体を使用します。**
低負荷から始めるためDX11、Lumenなし、Naniteなし、レイトレーシングなし、60fps上限です。
低スペックPC上の性能を保証するものではなく、対象機での計測が必要です。

コンパイルとマップ生成だけの場合：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Scripts\BuildAndRun.ps1 -BuildOnly
```


### TPSプレイヤーとモンスターの操作

ゲーム画面を一度クリックして入力フォーカスを与えてください。プレイヤーはカプセル衝突を持つ `ACharacter` で、頭・胴・骨盤・両腕・両脚を楕円体中心で組んだ丸い簡易人型です。カメラはSpringArmによる右肩越しTPS視点です。身体Yawは常にクロスヘア方向へ固定し、A/D/Sでも正面を維持したまま横歩き・後退します。右腕と銃口はカメラPitchへ追従します。

検証床は約50 m角です。モンスターは起動時から腕運動と歩行を行い、約9 m進むごとに180度反転して同じ区間を往復します。材質耐性と構造強度も常時有効で、これらをON/OFFするゲーム操作はありません。

画面下には8枠のホットバーを表示します。数字キーでは選択せず、**マウスホイールだけで装備を切り替えます**。選択中の枠を強調し、ホットバー下へ装備名を表示します。

| 枠 | 装備 | 動作 |
|---:|---|---|
| 1 | ハンドガン | 右手から実体弾を発射。着弾時に半径12 cmの弾痕 |
| 2 | 大口径銃 | 右手から実体弾を発射。着弾時に半径30 cmの大きな弾痕 |
| 3 | グレネードランチャー | 右手から実体弾を発射。着弾時に半径45 cmで爆発 |
| 4 | ドリル | 例外的な即時処理。クロスヘア方向へ半径20 cmの貫通穴 |
| 5 | 修復ツール | クロスヘア方向の欠損を半径20 cmで修復 |
| 6 | カッター | 左ドラッグで画面上に切断線を指定して平面切断 |
| 7 | 接合ツール | 自由破片 → 接合先の順にクリック |
| 8 | グラブツール | 自由破片を左ボタンで掴み、移動・投擲 |

通常弾・大口径弾・グレネードはすべて、まずカメラ中央のクロスヘアから照準点を求め、**プレイヤーの銃口からその照準点へ実際のProjectileを飛ばします**。カメラ位置から直接着弾処理する方式ではありません。

| 操作 | 動作 |
|---|---|
| マウス移動 | TPSカメラとクロスヘア方向を変更 |
| マウスホイール | ホットバーの前後スロットへ切替 |
| 左クリック / 長押し | 選択中の装備を使用。銃器は長押しで連射 |
| W / A / S / D | 前進 / 左ストレイフ / 後退 / 右ストレイフ |
| Shift + WASD | 走る |
| Space | ジャンプ |
| PageUp / PageDown | 肩越しカメラ距離を変更 |
| R | カメラ距離を標準へ戻して視点を正面へ戻す |
| Backspace | 開発中の復旧用としてモンスターを初期状態へ戻す |
| Esc / 右上の× / Alt＋F4 | 終了 |

### 弾痕から貫通までの検証

ホットバーでハンドガンまたは大口径銃を選択し、同じ場所へ繰り返し射撃します。弾は右手の銃口から飛翔し、命中した時点で初めて体積を削ります。表面のくぼみが奥へ進み、最終的に穴が貫通することを確認できます。

ハンドガンは弾痕半径12 cm、大口径銃は30 cmです。削り込み深さには常時有効な材質耐性が適用され、腕・脚は標準、胴体中央はx2、頭部はx4の耐性です。自由破片に命中した場合は弾痕に加えて命中方向のImpulseも与えます。

### 穴あけ・修復の検証

ホットバーの**ドリル**は弾ではなく、クロスヘア方向へ直接円柱状の貫通穴を作る例外的なツールです。**修復ツール**は指定範囲に材料を戻します。

修復は操作履歴のUndoではなく、各Pieceが保持する修復上限の内側へ材料を追加する処理です。分離前の別Piece領域まで再生したり、切断面を越えて腕を自動再接続したりはしません。

### 構造強度・荷重破断の検証

構造強度は常時有効です。完全に非連結になる前でも、重い部分を支える接続断面が細くなりすぎた場合に自動破断します。最初の検証では、各X/Y/Z断面について「断面の材料格子点数」と「その断面の小さい側に残る材料格子点数」を数え、`load / section >= 90` を破断条件にしています。小さい側の材料が120格子点未満の箇所は、先端形状などを誤判定しないよう対象外です。

これは有限要素法や実材料の応力計算ではなく、**残存断面に対する自己荷重の簡易指標**です。肩などを弾痕・穴あけで削り、細い材料だけで腕がつながった状態を作ると、トポロジ的な接続が残っていても閾値を超えた時点で弱断面に破断面を作り、支持を失った側をChaos破片として落下させます。ログには `AP5_STRUCTURAL_BREAK` と断面サンプル数、荷重サンプル数、比率、破断面位置を出します。

現段階では通常の固定体だけを対象にし、歩行・右腕関節モードの駆動PieceはPhysics Constraint側の破壊判定と競合しないよう構造強度判定から除外しています。

### 穴あけ・弾痕による自動分離の検証

1. `Backspace` でリセットし、腕と胴体のつながりが見える角度に回り込む。
2. `7` の弾痕モードで腕の付け根を繰り返し削る。穴が通っても周囲に材料が残っていれば腕は落ちない。
3. 狙う位置や視点を変えて残ったつながりも削る。最後のつながりを失うと腕が分離して落ち、画面の「分離」に増加した塊の数が出る。
4. `1` の貫通穴でも同じことを試す。落ちた破片も削ってさらに分離できる。

判定は**5 cm格子の材料の連結性**に基づきます。表面生成に使う四面体の辺に沿って材料のつながりを調べます。細い部分でも接続が残る限りは保持し、太さ・荷重・材質強度による破断はまだ扱いません。描画された三角形の辺を直接調べる方式ではなく、格子より細かいつながりは表現できません。

切断と同じく、初期の足裏付近の支持点を含む塊だけが固定を引き継ぎ、支持点から離れた塊は大きさに関係なく落ちます。既に落下中の破片から分離した塊は、すべて親の現在位置と落下速度を引き継ぎます。両脚とのつながりや支持点自体を削って失った胴体も固定解除します。ただし、重心・荷重から姿勢の安定性を判断する計算はまだありません。分離した破片はChaosの剛体として回転・衝突します。

分離しなかった弾痕・穴は従来どおり修復できます。分離が起きた場合は、その時点の各塊の形が修復上限になります。離れた腕を修復操作だけで再接続することはできません。破片数または連結成分数の上限を超える場合は、そのクリックの加工全体を取り消し、案内を表示します。

### 切断・落下・破片の再加工の検証

1. `Backspace` で全形状を戻す。
2. 観察カメラで、胴体と腕の位置関係が分かる角度にする。
3. `6` を押す。左ボタンを押し、腕を胴体から切り離す位置に線を引く。
4. 黄色い直線の位置と角度を確認して左ボタンを離す。右ドラッグに切り替えると切断を取り消せる。
5. 分離した塊が落下して床で停止すること、固定側と破片側の両方に断面があることを確認する。
6. リセットし、胴体の水平切断・斜め切断・穴を開けてからの切断も試す。
7. 床に落ちた破片を狙い、もう一度左ドラッグで切断する。さらに小さな破片にも同じ操作ができることを確認する。
8. 落下中の破片も切り、再分離した塊が元の位置と落下速度を引き継ぐことを確認する。
9. `1`で破片に穴を開け、`2`でその穴をふさぐ。元の体の位置に破片が再生しないことを確認する。
10. `Backspace` で床の破片も消え、最初の全身に戻ることを確認する。

ドラッグした短い線分の範囲だけでなく、**黄色い直線全体を奥まで伸ばした平面**が加工対象です。奥の腕や胴体も同時に切れるため、黄色い線を見て位置を決めてください。カメラを回り込ませることで切断面の奥行き方向も変えられます。案内の上での開始・終了、12ピクセル未満のドラッグでは加工しません。

切断は約3 cmの切りしろを設けた両側の閉曲面として生成します。格子間隔が5 cmなので断面の精度には限界があります。格子の四面体の辺に沿って材料のつながりを調べ、独立した塊をそれぞれ破片にします。同じ側にあってもつながっていない材料は別の破片です。

今回の制限：

- 固定の判定には、リセット時に採取した最下段の材料格子点（このモデルでは足裏付近）を使います。分離後にその支持点を残す塊だけが固定を引き継ぎます。最大の塊を無条件に固定する方式は廃止しました。両足をそれぞれ残す縦分割では両側が固定されます。一度固定解除された塊は、着地・修復・再切断しても固定に戻りません。支持点が一つでも残れば固定する検証用の方式で、片足立ちのバランスや細い接続の強度は未計算です。
- 分離した破片はChaosによる剛体シミュレーションで落下・回転し、床・固定本体・他の破片と衝突します。姿勢を人工的に回すのではなく、接触によって回転します。空中で初期角速度がゼロなら、接触するまで回転しない場合もあります。
- 本体・落下中の破片・着地後の破片は、すべて現在位置で再加工できます。同じ切断面や円柱範囲に入る複数の塊は同時に対象になります。着地後に加工して支えがなくなった塊は再び落下します。
- 修復は、その塊の**直近の分離時または接合時の形まで**に制限します。その後に開けた穴は、さらに分離・接合が起きていなければふさげますが、切断面を越えて元の全身を再生したり、分離前からあった穴を復元したりはしません。これは操作の取り消しではなく、その範囲内での材料の追加です。腕の再接続は修復とは別の接合モード（`8`）で行います。
- 蓄積する破片は最大32個です。上限を超える切断・穴あけ・弾痕は形状を変えずに拒否します。極端に細かい形状で連結成分数の上限に達した場合も切断を適用しません。
- 歩行・戦闘・加工状態の保存は未実装です。

`AP5_CUT` に切断の結果、`AP5_FRAGMENT_SLEEP` に物理計算が静止状態へ移った塊を記録します。メッシュ・衝突形状の再構築はイベント単位でログへ追記せず、低FPSフレームの処理時間集計に含めます。静止は必ずしも床への着地を意味しません。連続切断やリセット時の停止感も確認してください。破片にも再加工用の体積データを保持するため、描画だけだった前段階より破片数に応じたメモリ使用量は増えます。

### 破片の回転・衝突と背景の検証

1. `6` の斜め切断、または `7` の弾痕で腕を分離し、床に当たった後に傾く・転がる・止まるかを見る。
2. 別の破片も落とし、先に落とした破片や固定本体との衝突を見る。
3. 横になった破片を `1 / 2 / 6 / 7` で加工し、見えている位置と向きに加工が合うか確認する。
4. 落下中の再切断で、子の位置・向き・並進速度・角速度が引き継がれるかを見る。
5. 胴体または両脚を横断する切断で、足から離れた大きな上半身も落ちることを確認する。穴あけ・弾痕でも両脚との接続を削り切れば同様に落ちる。
6. `Backspace` で破片と物理状態が全てリセットされることを確認する。

衝突形状は、材料内部の5 cmセルを隣接する箱にまとめて生成します。穴や削った部分を覆う大きな凸形状にはしません。全頂点が材料内にあるセルを採用するため、**見た目の表面より衝突形状が数cm内側になり、床や他の物体に少しめり込んで見える場合があります**。セルが一つも収まらない薄片は内部の小箱で代用するため、接触の再現性は低くなります。精密な接触形状・質量分布・材質ごとの摩擦係数は次の検証対象です。

形状加工のたびに対象の衝突形状も同期して作り直します。物理更新による位置と回転を加工用データへ反映し、回転中の再加工にも使用します。CCDを有効にしていますが、細い破片のすり抜けや積み重ね時の振動、衝突形状再生成時の停止感は実機で確認してください。床は有限の範囲なので、外へ出た破片は落下を続けます。

背景は青灰色の単色です。背景だけに非ライティング材質を使い、床・ゴーレム・照明の色は変えていません。`BuildAndRun.ps1` は背景材質が未生成なら自動で作成します。既存のマップは保持します。

### 切った腕の再接合の検証

1. `Backspace` でリセットし、`6` で片腕を切り離して落とす。
2. `8` を押し、落ちた腕を左クリックする。選択中の破片に黄色い「接合元」マークが出る。
3. 胴体を左クリックする。腕を胴体に対する元の位置・向きへ瞬時に戻し、一つの加工可能な塊に統合する。
4. `1 / 7` で接合部付近を削る、`6` でもう一度切るなど、接合後も同じ加工ができることを確認する。
5. 切断前や落下後に腕へ開けた、接合部から離れた穴が接合後にも残ることを確認する。
6. 腕をさらに分割した場合は、隣り合う破片から順に接合してみる。

一つ目に選べるのは固定されていない破片です。接合先は固定本体でも自由な破片でも構いません。同じ破片をもう一度クリックするか `8` を押すと選択を解除します。別モードへの切り替えや全リセットでも解除します。選択中も破片は物理で動きます。

接合先が倒れている場合は、その**現在の姿勢を基準にした元の相対位置・向き**へ合わせます。接合先自体を初期位置へ戻す操作ではありません。接合後の固定状態・速度は接合先を引き継ぐため、固定本体へ戻した腕は本体と一緒に固定されます。この位置合わせは検証用の瞬間移動で、移動経路の衝突回避や運動量保存は行いません。

共通の分離元を持ち、元の配置で隣接する破片だけを接合します。通常の約3 cmの切りしろは、分離直前に材料が存在し、両側の現在の材料から1格子以内にある点だけを補って閉じます。接合部に接する小さな削れも補われる場合がありますが、離れた穴や第三の破片は再生しません。間の破片が欠けている場合や大きく削り取られた場合など、つながった一つの塊にできなければ位置・形状とも変更せず拒否します。その場合は選択を維持するので、別の接合先をクリックできます。

接合時の形が新しい修復上限になります。接合前から残っている穴は、その後の修復で元の全身へ戻る対象にはなりません。接合後に新たに開けた穴は修復できます。分離直前の体積データを共有して記録するためメモリ使用量が増えます。兄弟が全て再統合された分離履歴は解放し、切断・接合の単純な反復で履歴が増え続けないようにしています。

成功は `AP5_JOIN`、拒否理由は `AP5_JOIN_REJECTED` に記録します。自由な位置での手動接着、別のモンスターとの融合、関節の復元は今回の対象外です。

### 連射時の低FPSフレーム集計

連射時のヒッチ調査では、イベント単位の詳細ログを大量に残さず、**UEのエンジンフレーム境界ごとに処理時間だけをメモリ上で集計**します。フレーム時間は `FCoreDelegates::OnBeginFrame` から `OnEndFrame` までを実測します。起動直後はDynamicMesh Component生成・SceneProxy登録・RenderThread追従が集中し、通常プレイの連射性能と性質が異なるため、最初の120フレームはウォームアップとして集計対象外にします。

- 50 FPS未満、つまり1フレームが20 msを超えたフレームだけを集計対象にする。
- 各対象フレームで、処理カテゴリごとの合計時間を求める。同じ処理が1フレーム内で複数回呼ばれた場合は合算する。その処理が走らなかった低FPSフレームは0 msとして平均・最小へ含める。
- 各カテゴリについて、対象フレームにおける処理時間の**平均・最小・最大**だけをゲーム内部に保持する。イベント名、フレーム番号、着弾回数などは保存しない。
- `t.MaxFPS=60` 等による意図的な待機は `FPS制限待機`、OSスリープの超過分は `FPS制限待機超過` として分離する。両者の合計は `FApp::GetIdleTime()` と一致する。
- 計測対象外の時間は `その他（未計測）` として、OnBeginFrame→OnEndFrameの実時間から、計測済み処理時間とFPS制限待機を引いて求める。これによりUE本体、Chaos、ゲームスレッド上の未分類処理などが支配的な場合の目安にする。
- 集計ファイルは毎フレーム追記せず、30フレームごとを上限に `Saved/Logs/Ap5SlowFrameProfile.csv` へ**上書き**する。新しい低FPSフレームが無ければ書き込まない。
- プロファイルファイル自身の書き込み時間も `プロファイラI/O` として計測する。

現在の排他的カテゴリは、弾生成、弾補助判定、物理状態同期、体積編集・連結判定、表面生成、DynamicMesh頂点法線初期化、DynamicMesh頂点追加・法線設定、DynamicMesh三角形追加、描画チャンク管理、Mesh反映、衝突箱生成、衝突更新、物理衝突状態設定、物理Simulation切替、物理速度復元、コンポーネント生成、プロファイラI/O、FPS制限待機、FPS制限待機超過、その他（未計測）です。加えて、`参考_GameThread CPU`、`参考_GameThread Wait`、`参考_RenderThread CPU`、`参考_RenderThread Wait`、`参考_RHIThread CPU`、`参考_GPU` を記録します。参考値は並列実行されるため排他的カテゴリへ加算せず、`その他（未計測）` の差し引きにも使いません。隣接三角形の共有頂点IDを体積場のMarching Tetrahedra生成時に確定し、そのIndexed SurfaceをそのままDynamicMeshへ渡します。UE側でのTMap頂点検索を廃止し、法線はper-vertex normalとして保持します。

初回計測では、低FPSフレームの平均として「物理ボディ設定 約26 ms」「表面生成 約23 ms」「Dynamic Mesh構築 約16 ms」が突出し、弾生成・補助判定・体積編集は小さいことを確認しました。最適化後は弾補助判定が約0.001 ms、物理設定系が平均0.3 ms未満まで低下しました。Indexed Surfaceを直接DynamicMeshへ渡す方式では、頂点追加・法線設定が約0.29 ms、三角形追加が約2.29 ms、表面生成が約5.65 msまで低下しました。一方で `その他（未計測）` が大きく残りました。AP5は `t.MaxFPS=60` ですが、50 FPS未満の重いフレームでは既に16.7 msの予算を超えているため、FPS制限Sleepが発生せず `FPS制限待機=0` になることがあります。実測でも重いフレームでは待機0 msでした。直接インデックス表への変更後、表面生成は約1.2 ms、DynamicMesh三角形追加は約0.7 msまで低下しました。一方で `その他（未計測）` が平均約26 ms残ったため、UEが公開しているGame Thread、Render Thread、RHI Thread、GPUのフレーム時間を同じ低FPS統計へ参考値として追加しました。実測ではRender Thread CPUが低FPS時に突出し、GPUは約15 ms、RHI Threadは約1 ms未満だったため、全身DynamicMeshを毎回 `SetMesh` してRenderProxyを全面更新する構造が次の主因と判断しました。対策として、論理・物理上は1つのPieceのまま、描画をDynamicMeshチャンクへ分割し、形状署名が変わったチャンクだけ `SetMesh` する方式へ変更しました。物理ComponentはSimple Collision専用とし、描画チャンクはその子として追従します。80 cmではGame Threadは軽い一方でRender Thread/GPUが約15.8/15.6 ms、120 cmではRender Thread/GPUが約11.4/11.4 msまで下がる一方でGame Thread CPUが約19.3 msまで増えました。このトレードオフから現在は100 cmを中間点として採用し、更新範囲と描画Component数の均衡を取ります。Marching Tetrahedraで三角形を生成する時点でチャンク所属と形状署名も同時に生成し、描画更新側での全三角形再走査は行いません。

カテゴリ別の `Ap5SlowFrameProfile.csv` は各カテゴリにつき平均・最小・最大の3値だけを保持します。これは20 ms超の低FPSフレームだけを対象にします。最適化前後では「低FPSフレーム自体の発生回数」が変わるため、この条件付き平均だけを横比較しません。

別の小さい `Ap5FrameSummary.csv` に、ウォームアップ後の計測フレーム数、低FPSフレーム数、低FPS率、全フレーム時間の平均・最小・最大、低FPSフレーム時間の平均・最小・最大を保存します。これにより、「残った重いフレームの中身」と「重いフレームがどれだけ減ったか」を分けて評価します。100 cmチャンクでの連射実測では、8849フレーム中20 ms超は16フレーム（0.181%）、低FPSフレーム平均26.846 ms、最大50.714 msでした。低FPS時の参考値はGame Thread CPU約19.8 ms、Render Thread/GPUはいずれも約7.5 msで、残るヒッチは描画側よりGame Thread側が中心です。既知処理では体積編集・連結判定約5.8 ms、表面生成約4.7 msが大きく、今後さらに詰める場合は全グリッド処理の局所更新化が次候補です。

```text
項目,値
計測フレーム数,...
低FPSフレーム数,...
低FPS率_pct,...
全フレーム平均_ms,...
...
```

### 股関節・膝関節を使った簡易歩行

モンスターは起動時から「固定上半身＋右腕＋左右大腿＋左右下腿」の駆動Piece構成で歩きます。左右脚は約1.8秒周期で支持脚／遊脚を切り替え、遊脚側だけ膝を曲げます。支持足の実床Traceを使って足を床へ固定し、骨盤移動からActorの前進量を求めます。

約9 m進むとYawを180度反転し、その位置を新しい歩行原点として支持足を取り直します。50 m角の床端へ近づく前に反転するため、通常巡回では落下しません。足裏材料や実床支持を失った場合だけ従来どおり支持喪失を検出し、一定時間後にChaos転倒へ移行します。

右腕も同時に約3秒周期・±35度で動きます。歩行と腕運動を切り替えるキーはありません。

### 実体弾の飛翔・衝突・運動量の検証

ハンドガン・大口径銃・グレネードランチャーはすべてProjectileMovementで1800 cm/sの可視弾を発射します。銃口位置からクロスヘア照準点へ向けて飛ばすため、肩越しカメラでも射線の始点はプレイヤー側です。

弾自体は半径8 cm、寿命5秒、重力なしです。高速移動で薄い部位を飛び越えないよう、前フレーム位置から現在位置まで体積場に対する補助Sweepも行います。通常弾は着弾時に弾痕とImpulse、グレネードは着弾時に球状破壊を発生させます。

### 材質による弾痕・貫通速度の違い

材質耐性は常時有効で、ゲーム中に切り替えません。

| 領域 | 耐性 | 1発あたりの基準削り込み |
|---|---:|---:|
| 腕・脚・その他 | x1 | 約8 cm |
| 胴体中央 | x2 | 約4 cm |
| 頭部 | x4 | 約2 cm |

材質分類は現段階ではモデル局所座標による簡易マップです。密度・摩擦・爆発耐性などの本格的なボクセル材質属性はまだ持たせていません。

### 重心と支持範囲による転倒の検証

これまでは足裏の支持点が1点でも残っていれば本体を固定していました。今回から、自動取得した足裏支持については**現在残っている材料の重心を床へ投影し、その点が残存支持範囲から大きく外れた場合は固定を解除**します。

1. `Backspace` で通常状態に戻し、両脚がある状態では従来どおり立ったままであることを確認する。
2. `1` または `7` で片脚の付け根を削り、片脚を本体から完全に切り離す。
3. 残った片脚が床に接していても、上体の重心がその足の支持範囲から外れていれば本体全体がChaosへ移行して倒れることを確認する。
4. 逆に、左右に分かれた小さな塊など、それぞれの重心が自分の支持範囲内にある場合は固定が維持されることを確認する。
5. 倒れた本体は `G` で把持でき、`1 / 6 / 7 / 0` で現在姿勢のまま再加工できることを確認する。

現段階は厳密な剛体静力学ではなく、足裏付近の残存支持点をXYの矩形として近似し、重心投影がその範囲（5 cm格子1セル分の余裕付き）に入るかで判定します。初版の20 cm余裕では片脚だけ残った実モデルでも中央重心を支持扱いにしてしまったため、実機確認結果を受けて縮小しました。支持多角形、接触圧、摩擦、動的な慣性による転倒までは扱いません。一度不安定になってChaosへ移行した塊は、修復や着地だけでは自動的に静的固定へ戻しません。

### 分離破片の把持・移動・投擲の検証

ホットバーで**グラブツール**を選択すると、Chaos物理になった自由破片だけを掴めます。左ボタンを押している間はPhysics Handleでクロスヘア奥行き位置へ追従し、離したときに付いていた速度を保持して投擲できます。

固定本体や駆動中の関節Pieceは掴めません。ホイールで別装備へ切り替えると自動的に把持を解除します。

### 爆発弾による着弾位置の局所破壊と爆風

ホットバーの**グレネードランチャー**は銃口から実体弾を発射し、弾が衝突した位置で半径45 cmの球状破壊を発生させます。自由になった塊には爆心から外向きへ550 cm/sの簡易初速度を与えます。

爆風の圧力波・遮蔽・距離減衰・質量依存はまだ未実装です。形状変更と分離判定は他の加工と同じPiece/Volume処理を使います。

### 右腕の関節動作中の加工検証

右腕関節はモンスターの通常状態として常時動作します。右肩をroot側に残し、上腕・前腕・手をDriveId 5の駆動Pieceとして分離し、肩Pivotを中心に往復させます。歩行用のDriveId 1〜4とは独立しているため、腕運動と歩行を同時に実行できます。

右腕へ射撃・ドリル・カッターなどを当てた場合も現在姿勢で加工します。拘束部を失った破片は自由化し、転倒時には右肩もPhysics Constraintへ切り替えます。

### 今後の検証順

1. コード生成した静止モンスターと観察操作（ユーザー確認済み）。
2. 指定位置の穴あけと、材料を足してふさぐ修復（前段階の実装はユーザー確認済み）。検証用リセットは修復と区別する。
3. 任意の位置で切断し、分離した破片を落下させる（初回切断・共通化後の再加工はユーザー確認済み）。
4. 分離破片の回転・衝突・支持を失った胴体の落下（転がりと固定解除はユーザー確認済み）。
5. 切れた腕の再接続（ユーザー確認済み）。別のモンスターとの融合は対象外。
6. 腕一本の関節動作そのものはユーザー確認済み。関節境界を連続変形にする方式はSkeletal Mesh検討時まで保留する。
7. 爆発による球状破壊・自動分離・爆風はユーザー確認済み。
8. Chaos破片の把持・移動・投擲はユーザー確認済み。
9. 重心投影と支持範囲による片足立ち・転倒はユーザー確認済み。
10. 材質による弾痕深さ・貫通発数の差はユーザー確認済み。弱点設定とは独立した検証値として扱う。
11. 実体弾の飛翔・移動破片への衝突・命中時インパルスはユーザー確認済み。
12. 実体弾の継ぎ目すり抜け対策、着弾式爆発弾、長押し連射はユーザー確認済み。
13. 低FPSフレームだけを対象に処理時間の平均・最小・最大を集計し、連射時ヒッチの支配要因を特定する（今回の確認対象）。

- 回転・ズーム・穴あけ・修復・切断・落下・全リセットを上記の手順で確認する。
- 一般ログは `.local/logs/run.log` または `Saved/Logs/Ap5.log`。性能確認は固定サイズの `Saved/Logs/Ap5SlowFrameProfile.csv` を使用する。

| 問題 | 確認するもの |
|---|---|
| UEが見つからない / 別バージョン | `Setup.ps1 -EngineRoot` で5.6のパスを指定 |
| MSVC / SDK不足 | Visual Studio Installerで上記コンポーネントを追加 |
| ビルド失敗 | `.local/logs/build.log` の最初のエラー |
| マップ生成失敗 | `.local/logs/create-map.log`。Python/Editor Scriptingプラグインの有効化を確認 |
| 黒画面 / 起動失敗 | `.local/logs/run.log`、`Saved/Logs/Ap5.log`、GPUドライバ |
| パッケージ失敗 | `.local/logs/package.log` |
| DLLが使用中 | 起動中のAp5ゲームとUEエディタを終了して再実行 |

ログは次回実行で上書きされるので、問題が出たら保存して共有してください。`AP5_SAMPLE_READY` は生成完了の目印であり、描画・衝突の正しさは実画面でも確認してください。

## 構成と変更箇所

- `Source/Ap5/Ap5GameMode.cpp`：床と照明、モンスターの配置。
- `Source/Ap5/Ap5FrameProfiler.h/.cpp`：低FPSフレームだけを対象に処理時間の平均・最小・最大を集計し、固定サイズCSVへ低頻度で上書き。
- `Source/Ap5/Ap5Monster.cpp`：部位の寸法・位置と描画メッシュの更新（単位cm）。
- `Source/Ap5/Ap5Volume.h`：UEに依存しない体積データ、穴あけ・局所修復・表面生成・切断・連結判定・落下計算。
- `Source/Ap5/Ap5Pieces.h`：本体と破片の共通データ、現在位置での一括加工、再切断時の状態継承。
- `Source/Ap5/Ap5Observer.cpp`：観察カメラ、操作、画面上の案内。
- `Config/DefaultEngine.ini`：描画・既定マップ・GameMode。
- `Scripts/CreateMap.py`：空のマップを生成。既存マップは上書きしません。
- `Scripts/Setup.ps1`：Windows依存環境の導入・確認。
- `Scripts/BuildAndRun.ps1`：ビルド・初回マップ生成・ゲーム起動。
- `Scripts/Package.ps1`：配布用Shippingビルド。
- `.local/`、`Content/Generated/`、`Binaries/`、`Intermediate/`、`Saved/`、`Builds/`：ローカル生成物。Git対象外。

生成マップはC++サンプル用の空マップです。手編集するようになったら `Content/Maps/` などGit管理する場所へ保存し、マップ設定を変更してください。
現在 `.uasset/.umap` はGit LFS設定を用意していますが、コミットされたバイナリアセットはありません。将来独自アセットを追加するときにGit LFSを導入してください。

その後のモンスター生成・観察操作・透け描画修正・別ログウィンドウの抑止・穴あけ・修復・白い材質と視点反転はユーザー確認済みです。共通化後の破片の再加工についてもユーザーからOKの報告を受けています。弾痕モードもユーザーからOKの報告を受けています。穴あけ・弾痕による自動分離もユーザー確認済みです。Chaosによる破片の転がりと背景描画はユーザー確認済みです。支持点による固定解除もユーザー確認済みです。破片の選択・接合とその後のUE上での再加工もユーザー確認済みです。右腕の関節動作、従来の爆発による局所破壊・爆風、破片把持・投擲、重心・支持範囲による転倒、材質による弾痕耐性差、実体弾の基本的な飛翔・衝突はユーザー確認済みです。動作中の加工・切断・再接合の詳細、今回追加した実体弾の補助スイープ・着弾式爆発弾・長押し連射、およびShippingパッケージはWindows/UEで未検証です。従来の確認結果を今回の動作保証とは扱いません。
体積演算のC++コードはLinuxで直接コンパイルし、貫通・局所修復・外形制限・斜め加工後の閉曲面・リセットに加え、水平/垂直/斜め切断、穴のある断面、連結判定、落下と床での停止を確認しています。UEとの接続・UHT/MSVCビルド・描画・入力・実機性能はこのテストでは確認できません。
再加工については、ゲームと共通のコレクション処理をテストし、着地後・落下中の再切断、位置と速度の継承、移動した破片の穴あけ・修復、上限超過時に一部だけ切断されないこと、全リセットを確認しています。
リポジトリ構成の整合性とマップ生成スクリプトの分岐は、標準Pythonだけのテストで検証します。
PowerShellの構文検証用スクリプトも付属しますが、構文成功はUE動作保証ではありません。
GitHub Actionsにも同じテストとPowerShell 5.1/7の構文検証、および独立したC++体積演算テストを設定しています。UE本体を使うCIビルドではありません。

自動分離については、つながりが残る穴で分離しないこと、穴あけと弾痕の反復での分離、分離後の閉曲面・落下・位置と速度の継承、修復上限、上限超過時の全対象の変更取り消し、材料の全消去をC++テストで確認しています。

物理用データについては、回転・平行移動後の穴あけ／弾痕／修復／切断が局所座標での加工と一致すること、分離後の姿勢と速度場の継承、衝突箱が穴の中心をふさがないことをC++テストで確認しています。Chaosの接触・回転・静止やUEの材質コンパイルはこのテストでは検証していません。

支持判定の回帰テストでは、大きい上半身の固定解除、左右それぞれの足元を残す塊の固定、分離せず支持点だけ削った場合の固定解除、修復で再固定されないこと、リセットで初期の固定状態へ戻ることに加え、両足支持での安定、上体が中央のまま片足だけ残った状態の自由化、さらに重心が偏った状態の自由化、明示アンカーの従来互換を確認しています。

接合のC++テストでは、回転・移動後の破片の選択、接合先への姿勢合わせ、接合部以外の穴の保持、切りしろ補完後の閉曲面、再切断・再接合、多段分離後の接合、不正な接合の無変更拒否、不要になった履歴の解放を確認しています。

関節動作のC++テストでは、切りしろ無しの関節分割、回転・移動した駆動腕への加工、切断時に肩側だけが拘束を維持すること、自由化した先端への速度・角速度継承、駆動側への再接合を確認しています。

爆発のC++テストでは、球状の材料除去、爆発による自動分離、支持点を残す側の固定維持、自由破片への放射状速度、破片上限超過時の形状・速度のロールバックを確認しています。
